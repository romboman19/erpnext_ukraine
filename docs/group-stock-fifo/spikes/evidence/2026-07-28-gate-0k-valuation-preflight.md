# Gate 0k — preflight валюаційної черги: evidence, 2026-07-28

## Результат

`PASS`. §42.1 питання 7 закрите: **черга не потребує реконструкції.** ERPNext
зберігає її як JSON на кожному Stock Ledger Entry і постачає клас, яким сам її
споживає. Прогін останнього рядка через `FIFOValuation` дає точні bins
наступного списання — у пам'яті, без жодного запису.

## Механізм

```python
queue = json.loads(latest_sle.stock_queue)      # [[2.0, 1000.0], [3.0, 1100.0]]
replay = FIFOValuation([list(row) for row in queue])
consumed = replay.remove_stock(4)               # [[2.0, 1000.0], [2.0, 1100.0]]
```

Це не власна реалізація FIFO, а **той самий клас**
(`erpnext.stock.valuation.FIFOValuation`), який ERPNext викликає у
`stock_ledger.py`. Розбіжність між передбаченням і фактом можлива тільки якщо
зміниться сам ERPNext — і тоді вона зміниться в обох місцях одночасно.

Код: [`preflight.py`](../../../erpnext_ua/group_stock_fifo/spikes/preflight.py),
[`gate_0k.py`](../../../erpnext_ua/group_stock_fifo/spikes/gate_0k.py).

```bash
bench --site postest.local execute erpnext_ua.group_stock_fifo.spikes.gate_0k.run \
  --kwargs '{"confirm_site":"postest.local","confirm_write":"RUN_GATE_0K"}'
```

## Прогін A — передбачення проти фактичної книги

Пул ФКРВ: два шари, 2 × 1000 і 3 × 1100. Запит на 4 одиниці перетинає обидва.

| | Значення |
|---|---:|
| черга до операції | `[[2, 1000], [3, 1100]]` |
| передбачені bins | `[[2, 1000], [2, 1100]]` |
| **передбачена вартість** | **4200.00** |
| **фактична вартість SLE** | **4200.00** |
| черга змінилася від передбачення | **ні** |

Останній рядок важливий окремо: preflight нічого не пише. Це знімає єдиний
серйозний недолік третього кандидатного підходу з ADR-007 (dry-run у savepoint),
який подвоював би запис на гарячому шляху.

## Прогін B — некласифікований залишок

У пул додано 1 одиницю по 1500 **без виміру** — саме так виглядав би неконтрольований
Stock Entry у GSF-склад.

```text
unclassified_qty = 1.0
error_code = UNCLASSIFIED_GSF_STOCK
ok = false
```

Preflight зупиняє чек **до** будь-якого списання. Зверніть увагу, що вартісна
перевірка при цьому проходить (`delta = 0.00`): шар-порушник стоїть у черзі
третім і на списання чотирьох одиниць ще не впливає. Якби перевірка була лише
вартісною, ця ситуація пройшла б непоміченою і вибухнула на наступному чеку.

## Прогін C — план не збігається з чергою

План каже 4000, черга дає 4200.

```text
delta = 200.0
error_code = VALUATION_QUEUE_DIVERGENCE
ok = false
```

Розбіжність повертається як помилка, а не як warning — §44 забороняє пропускати
valuation mismatch попередженням.

## Знахідка: один рядок не може охопити два шари

Перша редакція гейта списувала 4 одиниці **одним** рядком Material Issue з
виміром першого шару. ERPNext відхилив:

```text
InventoryDimensionNegativeStockError: 2.0 units ... are required in
Warehouse HUNTER.rv Пул - ФКРВ with the inventory dimension:
gsf_spike_layer: GSF-LAYER-00014
```

Рядок оголошує один шар і просить більше одиниць, ніж той шар містить.

§14.4 («один Material Issue на кожну source Company, з окремими rows за layer»)
і §18.2 («окремий stock row для кожного slice») читалися як рекомендації щодо
акуратності. Насправді **платформа їх вимагає**: ліниву однорядкову реалізацію
неможливо написати навіть навмисно. Це рідкісний випадок, коли вимога ТЗ
підпирається валідацією ядра.

Наслідок для коду: `issue_layers_to_clearing` приймає перелік `(шар, кількість)`
і будує рядок на кожен шар.

## Межі доказу

- Метод оцінки — FIFO. Для Moving Average `stock_queue` має інший зміст, і
  preflight у цьому вигляді до неї не застосовний; GSF на середньозважену не
  розрахований.
- Перевірено один Item в одному складі. Preflight за §17.2 виконується на кожну
  трійку source Company / Item / Warehouse окремо — цикл, а не інша логіка.
- Не перевірено дві решти перевірки §17.2: `PENDING_REPOST` (у стеку немає
  scheduler) і `NEGATIVE_STOCK_RISK`. Обидві читаються з наявних таблиць і не
  залежать від механізму черги.
- Serial/Batch не задіяні. Для них ERPNext веде чергу в
  `Serial and Batch Bundle`, а не в `stock_queue` — окреме питання.
