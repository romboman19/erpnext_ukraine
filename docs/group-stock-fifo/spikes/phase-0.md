# Phase 0 — протокол технічного спайка GSF

## Мета

Довести найризикованіші припущення моделі шарів до реєстрації production hooks
і створення DocType. §42 базового ТЗ лишається чинним: без доказів код не
пишеться.

Результат кожного гейта:

1. відтворюваний скрипт або тест;
2. фактичні Stock Ledger / GL записи (для гейтів на сайті);
3. рішення в ADR із fallback;
4. регресійний тест;
5. статус `PASS`, `FAIL` або `BLOCKED` — без оптимістичних припущень.

Вихід фази: `GO`, `GO WITH CONSTRAINTS` або `REVISE ARCHITECTURE`, і прийняті
ADR за §40 базового ТЗ — [каталог](../adr).

## Фікстури

Мультифопний пул будується
[`spikes/fixtures.py`](../../../erpnext_ua/group_stock_fifo/spikes/fixtures.py),
локація `HUNTER.rv м.Рівне`:

| ФОП | Abbr | Група ЄП | Ставка | ПДВ |
|---|---|---|---|---|
| Козярчук Роман Вячеславович | ФКРВ | 3 | 5% без ПДВ | ні |
| Козярчук Вячеслав Володимирович | ФКВВ | 2 | Фіксована ставка | ні |
| Кравчук Іван Валентинович | ФКІВ | 3 | 3% з ПДВ | **так** |

Третій ФОП узятий платником ПДВ навмисно — без нього не перевіриш змішаний
кошик, а це один з основних кейсів мультиФОПу. РНОКПП синтетичні (префікс
`999999900*` з коректною контрольною сумою).

На кожен ФОП створюється склад пулу `HUNTER.rv Пул - <abbr>` і склад
комплектування `HUNTER.rv Комплектування - <abbr>` (§7.3), плюс один спільний
item `GSF-PHASE0-ITEM`.

```bash
bench --site postest.local execute erpnext_ua.group_stock_fifo.spikes.fixtures.build \
  --kwargs '{"confirm_site":"postest.local","confirm_write":"BUILD_GSF_PHASE_0"}'
```

`state` показує поточний стан без запису, `teardown` прибирає створене й
відмовляється чіпати те, що вже має рухи по складу або компанію, яка існувала
до фікстури. Inventory Dimension тут не створюється — її приносить гейт 0d,
щоб 0b і 0e працювали на незмінній схемі.

## Вердикт Phase 0

**`GO WITH CONSTRAINTS`**, 2026-07-27, оновлено 2026-07-28. Дев'ять гейтів
закриті (вісім за §42 плюс доданий 0k), обидва залишки — не блокери: 0h у
частині форм і 0i у частині хуків, яких ще немає.
Стан ADR за нумерацією §40 базового ТЗ:

|---|---|---|

| [002](../adr/0002-inventory-dimension-coexistence.md) | Inventory Dimension coexistence | `Accepted` |
| [003](../adr/0003-exact-value-intercompany-reallocation.md) | Exact-value reallocation | `Accepted` |
| [004](../adr/0004-posting-order.md) | Posting order | `Accepted` |
| [005](../adr/0005-balance-sheet-clearing-accounting.md) | Clearing accounting | `Accepted` |
| [006](../adr/0006-stage-lane-isolation.md) | Stage lane isolation | `Accepted` |
| [007](../adr/0007-valuation-queue-preflight.md) | Valuation queue preflight | `Accepted` (гейт 0k) |
| [008](../adr/0008-transaction-boundary.md) | Transaction boundary | `Accepted` |
| 009 | Return FIFO policy | не написаний |
| 010 | Backdated/revaluation policy | не написаний |
| 011 | CC compatibility contract | скасований ревізією |
| [012](../adr/0012-pos-prro-saga.md) | POS/PRRO saga | `Proposed` |

| [014](../adr/0014-idempotency-and-stable-keys.md) | Ідемпотентність і стабільні ключі | `Accepted`, поза §40 |

ADR-007 закритий гейтом 0k 2026-07-28 — ризик №1 у §35 має робочу мітигацію, а
не заплановану. Незаписаними за §40 лишаються 009 (повернення) і 010
(backdated/revaluation); 011 скасований ревізією.

Модель шарів витримала: вартість переноситься між ФОП точно, падіння відкочує
все, шар простежується в книзі, наскрізний сценарій §37.1 дає рівно 6500.

Обмеження, з якими дозволено починати Phase 1:

1. **Один checkout на одну staging lane одночасно** —
   [ADR-006](../adr/0006-stage-lane-isolation.md) за §7.2/§9.8. Lane —
   довгоживучий склад із `lock_token` і статусом; zero-check є передумовою
   локу, а `DIRTY` ніколи не чиститься автоматично. Ранній варіант «склад на
   кожен чек» відкликано: він давав ту саму гарантію, але не мав де зберігати
   стан `DIRTY`, який саме й має пережити невдалий чек.
2. **Документи перепризначення подаються в порядку аллокатора** — порядок подачі
   і є tie-breaker при однаковому timestamp (0f).
3. **Вартість читається з фактичного SLE**, ніколи з реєстру шарів: вимір
   позначає книгу, але не керує списанням (0c, 0d).
4. **Ідемпотентність не спирається на імена документів ERPNext** — серія
   відкочується при видаленні (0e).
5. **Спільний аллокатор**, GSF як другий адаптер кандидатів; потрібен адитивний
   `GSF_LAYER → OWN` і зняття двозначності `CandidateQuery.company` (0g).
6. **Порядок створення вимірів фіксується явно**, а власний `after_migrate`-патч
   прибирає GSF-поле з комісійних DocType (0d,
   [ADR-002](../adr/0002-inventory-dimension-coexistence.md)).
7. **Клірингових рахунків два, не один** — `Due From` і `Due To` плюс dimension
   `Counterparty Accounting Company` за §15.3
   ([ADR-005](../adr/0005-balance-sheet-clearing-accounting.md)).

Базове ТЗ v1.0 залито в репозиторій 2026-07-27
([`spec-v1.0.md`](../spec-v1.0.md)), тому модель даних Phase 1 більше не є
блокером. Розбіжності між ТЗ, ревізією та доказами Phase 0 зведені в
[`spec-reconciliation.md`](../spec-reconciliation.md) — там же колізія
нумерації ADR і перелік розділів, яких Phase 0 не торкалася (найбільший —
§17 preflight valuation).

Податкова оцінка схеми `MANAGEMENT_REALLOCATION` — рішення власника бізнесу та
його бухгалтера, не предмет цього проєкту. Питання зняте з переліку.

Розрахунки між ФОП питанням не є: §15.2 і §37.23 описують **звірку за
контрагентом** і елімінацію на рівні групової звітності, а не платіж. Накопичений
залишок — очікувана поведінка
([ADR-005](../adr/0005-balance-sheet-clearing-accounting.md)).

## Виконані гейти

### 0b + 0a — точність перенесення вартості

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0b-exact-value-transfer.md`](evidence/2026-07-27-gate-0b-exact-value-transfer.md).

Вартість переноситься між ФОП без втрат навіть тоді, коли цільовий склад уже
оцінений інакше, і навіть коли собівартість не ділиться націло. P&L обох
ваучерів = 0, тому 0a закритий тим самим прогоном.

Гейт додав інваріант, якого немає в ревізії ТЗ: **Sale Stage має містити лише
поточний чек**, бо черга FIFO цільового складу впорядкована за надходженням у
нього і не зобов'язана збігатися з вибором глобального FIFO. Перевіряється
гейтом 0c.

### 0c — COGS зі Sale Stage

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0c-sale-stage-cogs.md`](evidence/2026-07-27-gate-0c-sale-stage-cogs.md).

Продаж зі складу, що містить лише поточний чек, списує рівно підготовлену
вартість — 2000 проти 2000. Продаж із того самого складу, де лежала ще одна
старіша одиниця по 1500, списав **2500**, попри те що рядок був явно позначений
підготовленим шаром.

Звідси головний висновок хвилі 2: **Inventory Dimension не визначає
собівартість**, вона лише валідує залишки. Черга FIFO живе на рівні
`item + warehouse`, і мітка шару в SLE — це запис постфактум.

Тому:

- §16 («вартість з фактичного SLE») — єдиний робочий спосіб, а не обережність;
- «Sale Stage містить лише поточний чек» стає жорстким інваріантом: порушення
  дає грошову помилку в собівартості й податковій базі ФОПа;
- один Sale Stage на компанію не працює на точці з кількома касирами. Потрібен
  склад комплектування на касу, на чек, або сериалізація чеків ФОПа — відкрите
  питання до ADR-002 і касової саги;
- логічне резервування GSF не рятує: ERPNext про нього не знає.

### 0d — вимір шару в книзі

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0d-layer-dimension.md`](evidence/2026-07-27-gate-0d-layer-dimension.md).

Вимір доїжджає до SLE на всіх трьох документах ланцюжка, включно з продажем.
Дві Inventory Dimension співіснують — це половина 0h.

Дві знахідки, які змінюють план:

- вимір на `Stock Entry Detail` — це **пара полів**: `gsf_spike_layer` для
  вихідної ноги і `to_gsf_spike_layer` для вхідної. Помилка fail-closed, але
  падає наступний документ, а не той, що помилився;
- `apply_to_all_doctypes = 1` засіває поле й на комісійні DocType (8 таблиць),
  причому результат залежить від порядку створення вимірів. Вирішено в
  [ADR-002](../adr/0002-inventory-dimension-coexistence.md):
  `apply_to_all_doctypes` лишається (явного переліку кількох DocType платформа не
  підтримує), а власний патч прибирає GSF-поле з чужих DocType одразу після міграції.

### 0e — атомарний rollback

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0e-atomic-rollback.md`](evidence/2026-07-27-gate-0e-atomic-rollback.md).

Виняток після подачі Sales Invoice знімає issue, receipt і продаж разом зі
складською книгою та GL. Окремої компенсації для SLE не потрібно.

Гейт додав вимогу до ідемпотентності: **імена документів ERPNext не є
стабільними ключами** — `delete_doc` найновішого документа повертає лічильник
серії назад, і номер повторно видається наступному документу. Стабільні ключі
GSF мають бути власними, як у комісійному модулі.

### 0k — preflight валюаційної черги

`PASS`, 2026-07-28.
Evidence: [`2026-07-28-gate-0k-valuation-preflight.md`](evidence/2026-07-28-gate-0k-valuation-preflight.md).

Чергу не треба відтворювати: ERPNext зберігає її як JSON у
`Stock Ledger Entry.stock_queue` і постачає клас `FIFOValuation`, яким сам її
споживає. Прогін останнього рядка через цей клас передбачив 4200 — рівно те, що
потім списала книга, і без жодного запису.

Обидві відмови за §17.2 працюють: некласифікований залишок дає
`UNCLASSIFIED_GSF_STOCK`, розбіжність плану з чергою — `VALUATION_QUEUE_DIVERGENCE`.
Причому в прогоні B **вартісна перевірка проходить**, а ловить порушення саме
перевірка на некласифікований залишок — суто вартісний preflight пропустив би це.

Побічна знахідка: **рядок Material Issue не може охопити два шари** — вимір
відхиляє за негативним залишком. §14.4 і §18.2 виявилися вимогою платформи, а
не рекомендацією.

### 0f — розведення однакових timestamp

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0f-timestamp-ties.md`](evidence/2026-07-27-gate-0f-timestamp-ties.md).

При однаковому `posting_datetime` списується шар, поданий першим — стабільно у
трьох прогонах. Ризик непередбачуваного порядку знято, натомість з'явилося
правило: подавати документи перепризначення в порядку аллокатора. Субсекундні
зсуви часу, які пропонувалися як запобіжник, не потрібні.

### 0j — наскрізний сценарій

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0j-end-to-end.md`](evidence/2026-07-27-gate-0j-end-to-end.md).

Три ФОП, шість одиниць, план від справжнього `allocate_global_fifo` на
собівартостях, прочитаних зі складської книги. ERPNext списав рівно
заплановані **6500**. Шар продавця пішов останнім — заборона seller-first FIFO
працює й на реальних даних.

### 0g — спільний аллокатор

`PASS`, 2026-07-27.
Evidence: [`2026-07-27-gate-0g-shared-allocator.md`](evidence/2026-07-27-gate-0g-shared-allocator.md).

Другий аллокатор не пишеться: `allocate_global_fifo` не приймає `company`, і
GSF-скоуп задається адаптером кандидатів. Разом із цим закрито сервісний рівень
0i (ізоляція доменів тримається на `GSF Warehouse Binding`) і логічний рівень
0f (порядок GSF детермінований незалежно від ERPNext).

Побічні вимоги, які гейт породив:

- адитивний запис `GSF_LAYER → OWN` у `SOURCE_METHOD_RELATIONSHIP_MODEL`;
- `CandidateQuery.company` означає продавця для GSF і фільтр для CC — двозначність
  треба зняти явно;
- інваріант і тест на `GSF Warehouse Binding`;
- доменна помилка замість голого `KeyError` на чужому лоті.

## Що лишається поза Phase 0

Гейти доводять складську й бухгалтерську механіку. Вони **не** відповідають на
питання, які закривають окремі домени:

- правила вибору платника між ФОП (залишок ліміту, група ЄП, КВЕД, тип оплати);
- кілька ПРРО різних ФОП на одній фізичній точці;
- змішаний кошик, де частина позицій іде на ФОП з ПДВ;
- чи потрібен документ погашення зустрічних залишків між ФОП — продуктове
  рішення власника, механіка накопичення сама по собі коректна.
