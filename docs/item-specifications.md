# ТЗ: Модуль характеристик товарів (Item Specifications)

**Апка:** `erpnext_ua` (репозиторій `romboman19/erpnext_ukraine`)
**Новий модуль:** `ua_item_specs`
**Статус:** реалізовано етапи 1–6 (див. розд. 11 і «Відхилення від ТЗ» наприкінці)

---

## 1. Мета

Повноцінний механізм ведення характеристик товару: довідник характеристик, обов'язковий набір
на рівні товарної категорії, заповнення значень у картці товару, типізація, валідація, пошук і звітність.

### Функціональні вимоги

1. Характеристики створюються й ведуться в **окремому довіднику**. У товарі — лише вибір і заповнення значення.
2. На рівні **товарної категорії** задається мінімальний **обов'язковий** набір характеристик.
3. При створенні **товару** обов'язкові характеристики автоматично підставляються у форму й вимагають заповнення.
4. Користувач може **додати додаткові** характеристики понад обов'язковий набір.
5. Характеристики мають **типи**: короткий текст, довгий текст, HTML, ціле число, дробове число,
   список (один вибір), мультичек (кілька значень), так/ні, дата.
6. Значення зі списків обмежені довідником — довільний ввід відхиляється.

### Чому не штатними засобами

| Механізм ERPNext | Чому не підходить |
|---|---|
| **Item Attribute** | Призначений для генерації варіантів (Item Variant): кожне значення множить кількість SKU. Характеристики варіантів не творять — вийде комбінаторний вибух. Залишається за своїм призначенням (Розмір, Колір). |
| **Website Item → Specifications** | Живе на доктайпі вебвітрини, а не в картці товару. Значення — простий текст: без типів, без обов'язковості, без валідації, без фільтрації. |
| **Custom Field на Item** | Десятки полів, з яких для конкретного товару заповнено одиниці. Форма стає непридатною; різні набори для різних категорій не підтримуються. |

## 2. Архітектура

П'ять доктайпів у модулі `ua_item_specs`:

```
UA Item Specification Group        довідник груп характеристик (для угруповання в UI)

UA Item Specification              довідник характеристик (master)
  └── UA Item Specification Option    (child) — дозволені значення для Select / MultiSelect

UA Item Group Specification        (child) → таблиця на Item Group — набір характеристик категорії

UA Item Specification Value        (child) → таблиця на Item — значення характеристик товару
```

Зв'язок з існуючими доктайпами — через **Custom Field** типу `Table`, без форку ERPNext:

- `Item Group` → поле `ua_specifications` (Table → `UA Item Group Specification`)
- `Item` → поле `ua_specifications` (Table → `UA Item Specification Value`)

> **Про префікс `UA`.** Функціонал не є україно-специфічним, але префікс тримає консистентність
> з рештою апки і страхує від колізії імен, якщо подібний доктайп колись з'явиться в ядрі ERPNext
> (імена доктайпів у Frappe глобальні).

## 3. Доктайпи — детальна специфікація

### 3.1 `UA Item Specification Group` (довідник груп)

**Naming:** `field:group_name` · **istable:** 0

| Поле | Тип | Обов'язк. | Опис |
|---|---|---|---|
| `group_name` | Data | ✔ (unique) | Напр. «Габарити», «Оптика», «Матеріали» |
| `display_order` | Int | — | Порядок секцій у картці товару |

Призначення — групувати характеристики в картці товару, щоб при 20+ рядках вони не були суцільним списком.

### 3.2 `UA Item Specification` (довідник характеристик)

**Naming:** `field:spec_name` · **istable:** 0 · **track_changes:** 1

| Поле | Тип | Обов'язк. | Опис |
|---|---|---|---|
| `spec_name` | Data | ✔ (unique) | Назва, напр. `Довжина леза` |
| `fieldname` | Data | ✔ (unique) | Технічний слаг, напр. `blade_length`. Regex `^[a-z][a-z0-9_]*$`. Використовується в API та інтеграціях |
| `spec_group` | Link → `UA Item Specification Group` | — | Група для UI |
| `field_type` | Select | ✔ | `Data`, `Text`, `HTML`, `Int`, `Float`, `Select`, `MultiSelect`, `Check`, `Date` |
| `unit` | Data | — | Одиниця виміру: `см`, `мм`, `г`, `Дж`. Зберігається окремо від назви й показується поряд зі значенням |
| `spec_precision` | Int | — | Знаків після коми. `depends_on: field_type == 'Float'` |
| `min_value` / `max_value` | Float | — | Межі валідації. `depends_on: field_type in ('Int','Float')` |
| `description` | Small Text | — | Підказка користувачу під полем |
| `is_active` | Check | — | default `1`. Неактивні не пропонуються до додавання; наявні значення зберігаються |
| `allow_in_filters` | Check | — | Виводити характеристику у фільтрах звіту/каталогу |
| `options` | Table → `UA Item Specification Option` | — | `depends_on: field_type in ('Select','MultiSelect')` |

**Валідація (`validate`):**
- `fieldname` — regex, унікальність, заборона зміни після створення (на нього спираються інтеграції).
- Для `Select`/`MultiSelect` таблиця `options` не може бути порожньою.
- Заборонити зміну `field_type`, якщо характеристика вже має значення в товарах — інакше дані
  «осиротіють» у колонці іншого типу. Зміна — лише через контрольований патч конвертації.

**`on_trash`:** заборонити видалення, якщо існують значення в товарах або посилання з категорій.
Замість видалення — `is_active = 0`.

### 3.3 `UA Item Specification Option` (child)

**istable:** 1

| Поле | Тип | Обов'язк. | Опис |
|---|---|---|---|
| `option_value` | Data | ✔, `in_list_view` | Значення, що зберігається |
| `option_label` | Data | — | Відображувана назва, якщо відрізняється від значення |
| `is_active` | Check | — | default `1`. Неактивне не пропонується, але наявні значення лишаються валідними |

Порядок — штатний `idx`.

**Валідація:** `option_value` унікальне в межах характеристики.

### 3.4 `UA Item Group Specification` (child → `Item Group`)

**istable:** 1

| Поле | Тип | Обов'язк. | Опис |
|---|---|---|---|
| `specification` | Link → `UA Item Specification` | ✔, `in_list_view` | |
| `spec_label` | Data | — | `fetch_from: specification.spec_name`, `read_only`, `in_list_view` |
| `field_type` | Data | — | `fetch_from`, `read_only`, `in_list_view` |
| `is_mandatory` | Check | — | `in_list_view`. Обов'язкова до заповнення в товарі |
| `default_value` | Data | — | Підставляється в новий товар |

**Валідація (`Item Group.validate`):** характеристика не може повторюватись у межах категорії.

### 3.5 `UA Item Specification Value` (child → `Item`)

**istable:** 1

| Поле | Тип | Опис |
|---|---|---|
| `specification` | Link → `UA Item Specification` | ✔, `in_list_view`, `search_index` |
| `spec_label` | Data | `read_only`, `in_list_view` |
| `field_type` | Data | `read_only`, `hidden` — потрібне для `depends_on` |
| `unit` | Data | `read_only` |
| `is_mandatory` | Check | `read_only`. Проставляється з набору категорії |
| `source` | Select | `Category` / `Manual`, `read_only` |
| `value_data` | Data | `depends_on: eval:doc.field_type=='Data'` |
| `value_text` | Text | `depends_on: field_type=='Text'` |
| `value_html` | Text Editor | `depends_on: field_type=='HTML'` |
| `value_int` | Int | `depends_on: field_type=='Int'` |
| `value_float` | Float | `depends_on: field_type=='Float'` |
| `value_select` | Data | `depends_on: field_type=='Select'`. Контрол підміняється на Select через JS |
| `value_multi` | Small Text | `depends_on: field_type=='MultiSelect'`. Зберігається як JSON-масив |
| `value_check` | Check | `depends_on: field_type=='Check'` |
| `value_date` | Date | `depends_on: field_type=='Date'` |
| `display_value` | Data | `read_only`, `in_list_view`, `search_index`. Обчислюється в `validate` |

**Обґрунтування типізованих колонок.** Альтернатива — одна текстова колонка `value` з динамічною
підміною контролу через JS. Компактніше, але:
- числа зберігаються як текст → неможливо коректно сортувати й фільтрувати (`довжина > 50`);
- підміна `fieldtype` для окремого рядка грида у Frappe — крихкий прийом, ламається між версіями.

Тому основний варіант — **типізовані колонки + `depends_on`**: жодного хака, коректні типи в БД,
штатна фільтрація у звітах. Щоб грид не рябів порожніми колонками, у `in_list_view` виводяться
**лише** `specification` + `display_value`; типізовані поля видно в розгорнутому рядку.

**`display_value`** — денормалізоване текстове подання для грида, пошуку і звітів:
- `Int`/`Float` → число + `unit` (`47 см`);
- `Select` → `option_label` або `option_value`;
- `MultiSelect` → значення через `, `;
- `Check` → `Так` / `Ні`;
- `HTML`/`Text` → перші 140 символів без тегів.

## 4. Успадкування по дереву категорій

`Item Group` — nested set (`lft`/`rgt`), тож набір характеристик **успадковується згори вниз**:
характеристики, задані на «Ножі», діють на «Ножі → Складані» без повторного оголошення.

Правила збирання ефективного набору для категорії `G`:

1. Отримати предків `G` від кореня до `G` включно.
2. Йти від кореня до листа, накопичуючи характеристики в `dict[specification]`.
3. **Нащадок перевизначає предка**: якщо характеристика оголошена і в батька, і в дитини —
   виграє запис дитини (його `is_mandatory` і `default_value`). Це дозволяє зробити
   характеристику обов'язковою лише для підкатегорії.
4. Порядок виводу: успадковані (від кореня) → власні; всередині рівня — за `idx`.
   Характеристика зберігає позицію **першого** оголошення, а значення — від найближчого нащадка.

**Кешування.** Результат кешується в `frappe.cache()` під ключем `ua_item_specs::group::{item_group}`.
Інвалідація в `on_update` доктайпів `Item Group` та `UA Item Specification`.

## 5. Серверна логіка

### 5.1 API (`erpnext_ua/ua_item_specs/api.py`)

```python
@frappe.whitelist()
def get_group_specifications(item_group: str) -> list[dict]:
    """Ефективний набір характеристик категорії з урахуванням успадкування."""

@frappe.whitelist()
def get_specification_options(specification: str) -> list[dict]:
    """Активні значення довідника: option_value, option_label."""

@frappe.whitelist()
def sync_item_specifications(item: str) -> dict:
    """Пересинхронізувати набір товару з його категорією.
    Додає відсутні обов'язкові, нічого не видаляє. Повертає перелік змін."""

@frappe.whitelist()
def copy_specifications_from_template(item: str) -> dict:
    """Перезаписати характеристики варіанта значеннями шаблону."""
```

### 5.2 Хуки

```python
doc_events = {
    "Item": {
        "validate": "erpnext_ua.ua_item_specs.item_hooks.validate_specifications",
    },
    "Item Group": {
        "validate": "erpnext_ua.ua_item_specs.item_hooks.validate_group_specifications",
        "on_update": "erpnext_ua.ua_item_specs.item_hooks.clear_specification_cache",
    },
}
```

`validate_specifications(doc, method)` виконує послідовно:

1. **Синхронізація з категорією** — дотягнути відсутні рядки обов'язкового набору
   (`source = "Category"`, `is_mandatory = 1`, підставити `default_value`).
   Рядки, додані вручну, не чіпати (`source = "Manual"`).
2. **Дублікати** — одна характеристика двічі в товарі → `frappe.throw`.
3. **Обов'язковість** — для кожного рядка з `is_mandatory = 1` відповідна типізована колонка
   має бути непорожньою. Інакше `frappe.throw` **одним повідомленням зі списком** усіх
   незаповнених, а не по одній помилці за раз.
4. **Валідація за типом:**
   - `Int` / `Float` — межі `min_value` / `max_value`, округлення до `spec_precision`;
   - `Select` — значення входить у `options` (враховуючи неактивні для вже збережених);
   - `MultiSelect` — коректний JSON-масив, усі елементи входять у `options`, без дублікатів;
   - `Date` — коректна дата.
5. **Обчислення `display_value`** для кожного рядка.

> **Критично:** валідація має бути **серверною**. Клієнтський JS — лише для UX;
> Data Import, REST API, патчі й `bench execute` минають JS повністю.

### 5.3 Зміна категорії існуючого товару

Зміна `item_group` **не видаляє** введені значення. Поведінка:
- додати обов'язкові характеристики нової категорії;
- наявні значення зберегти; ті, що більше не входять у набір, позначити `source = "Manual"`;
- нічого не видаляти автоматично — рішення про видалення приймає користувач.

### 5.4 Варіанти товару (Item Variant)

Характеристики (марка сталі, довжина клинка) зазвичай однакові для всіх варіантів шаблону,
бо варіанти різняться лише за `Item Attribute` (Розмір, Колір).

**Рішення:** рядки характеристик зберігаються **фізично на кожному Item** (і на шаблоні, і на варіанті).
При створенні варіанта набір **копіюється з шаблону**; на варіанті значення можна перевизначити.
Додатково — кнопка «Оновити з шаблону» для масової синхронізації після зміни шаблону.

Обґрунтування: альтернатива (read-through до шаблону) економить рядки, але вимагає join через
`variant_of` у кожному звіті й фільтрі каталогу. Дублювання рядків дешевше за ускладнення всієї звітності.

## 6. Клієнтська логіка

Файл: `erpnext_ua/public/js/item_specifications.js`

1. **`item_group` (change)** — виклик `get_group_specifications`, підстановка відсутніх
   обов'язкових рядків без втрати вже введених значень.
2. **`form_render` для `ua_specifications`** — для рядка з `field_type == 'Select'` підставити
   опції в контрол `value_select` (кеш відповідей у пам'яті сторінки).
3. **`MultiSelect`** — діалог із чекбоксами; результат серіалізується в JSON у `value_multi`,
   у гриді показується `display_value`.
4. **Фільтр Link-поля `specification`** — `get_query` виключає вже додані в товарі
   та неактивні (`is_active = 0`).
5. **Кнопки на формі Item:** «Оновити характеристики з категорії», «Оновити з шаблону» (для варіанта).

## 7. Масові операції

Окремий інструмент «Масове заповнення характеристик»:
- вибір категорії / фільтра по товарах;
- вибір характеристики;
- встановити значення для всіх відібраних товарів.

> **Не реалізовано** — винесено в окремий етап (див. «Відхилення від ТЗ»).

---

## 8. Звітність, пошук, портал

- **Query Report «Характеристики товарів»**: `Item` × `specification` × `display_value`,
  фільтри за категорією, характеристикою, значенням.
- **Числові фільтри** (`довжина ствола > 50`) працюють штатно по `value_int` / `value_float` —
  саме заради цього типізовані колонки.
- `search_index: 1` на `specification` та `display_value`.
- **Опційно (фаза 2):** одностороння синхронізація в `Website Item → Specifications`.

## 9. Права доступу

| Роль | Довідник характеристик і груп | Набір на категорії | Значення в товарі |
|---|---|---|---|
| `Item Manager` | читання | читання/запис | читання/запис |
| `System Manager` | повний | повний | повний |
| `Specification Manager` (нова) | повний | повний | читання/запис |

Логіка: створення нових характеристик — контрольована операція (впливає на всі товари),
заповнення значень — щоденна робота товарознавця.

### Критерії приймання

- [x] Характеристика створюється з усіма 9 типами; для `Select`/`MultiSelect` — зі списком значень.
- [x] У категорії задається набір; обов'язкові позначені.
- [x] Новий товар у категорії — обов'язкові характеристики підставлені автоматично.
- [x] Збереження товару з незаповненою обов'язковою — помилка **зі списком** усіх незаповнених.
- [x] Характеристики успадковуються від батьківської категорії; перевизначення в дочірній працює.
- [x] Додавання довільної характеристики понад набір працює; вже додані повторно не пропонуються.
- [x] Значення `Select` поза списком відхиляється; `MultiSelect` приймає кілька значень зі списку.
- [x] Валідація спрацьовує при імпорті через Data Import, не лише через UI.
- [x] Зміна категорії товару не знищує введені значення.
- [x] Варіант успадковує характеристики шаблону й дозволяє перевизначення.
- [x] Звіт фільтрує за числовою характеристикою (`>`, `<`).
- [x] Видалення використаної характеристики заборонено; деактивація працює.

## 12. Ризики та рішення

1. **Обсяг даних.** Десятки тисяч товарів × 5–15 характеристик = сотні тисяч рядків у child-таблиці.
   Для Frappe прийнятно, але звіти — лише через індекси (розд. 8).
2. **Зміна `field_type` після накопичення даних** — заборонена (розд. 3.2).
3. **Продуктивність форми.** При 30+ характеристиках на товар грид стає важким —
   тому групування через `spec_group` і `in_list_view` лише на двох колонках.
4. **Мова.** Назви характеристик і значень зберігаються однією мовою в довіднику.
   Друга мова — через штатний механізм перекладів Frappe, **не** через дублювання характеристик.
5. **`is_active = 0`** для використаної характеристики: значення показуються й лишаються валідними,
   але характеристика не пропонується до додавання в нові товари.

## Відхилення від ТЗ у реалізації

Зафіксовано свідомо; кожне — щоб не заводити другий механізм там, де в апці вже є усталений.

1. **Custom Field створюються в `install.py` (`ensure_item_spec_setup`), а не через
   `fixtures/custom_field.json`.** У `erpnext_ua` єдина фікстура — `role.json`; усі кастомні поля
   (POS, ПРРО, Item, Mode of Payment) створюються ідемпотентними `ensure_*` функціями з
   `after_install`/`after_migrate` через `create_custom_fields(..., update=True)`. Фікстура тут
   створила б другий, неузгоджений шлях і конфліктувала б при міграції.

2. **`utils.py` розділено на `domain.py` + `service.py`.** Це конвенція модулів `ua_price_tags`
   та `ua_receiving`: чисті правила (без `import frappe`) лежать у `domain.py` і покриті
   юніт-тестами, які виконуються без бенчу; усе, що торкається БД, кешу й дерева категорій —
   у `service.py`. Завдяки цьому логіка злиття наборів і `display_value` тестується у CI без сайту.

3. **Поле `precision` названо `spec_precision`.** `precision` — зарезервоване ім'я в моделі
   документа Frappe (`Document.precision()` — метод визначення точності поля). Поле з таким
   `fieldname` затінює метод і ламає округлення валют у контролері.

4. **Порожнє число.** У Frappe `Int`/`Float` не мають стану «порожньо» — незаповнене поле
   приходить як `0`, а не `None`. Тому для обов'язкових числових характеристик **`0` вважається
   заповненим значенням**. Інакше довелося б відхиляти легітимний нуль.

5. **Інвалідація кешу — по всьому префіксу `ua_item_specs::group::`**, а не по гілці нащадків.
   Категорії змінюються рідко, а точкова інвалідація гілки при переміщенні вузла nested set
   легко стає джерелом непомітних розсинхронів. Простіше й безпечніше скинути всі ключі модуля.

6. **Масове заповнення (розд. 7) не реалізовано** — це самостійний UI-інструмент, який
   доцільно рев'ювити окремо від ядра модуля.
